# 简历考点（爬虫工程师 · G 端政策数据）

> 每条都要能接住三层追问：**具体怎么做的 → 当时出了什么问题 → 怎么证明改好了**。
> 答案里的数字必须与 `site_full_show.md` 一致；改了简历记得回来同步。

## 一、政策采集与系统设计

### 1. 政策采集和电商采集最大的区别是什么？

- 站点形态：电商站少而深，政策站多而散（400+ 个政府门户与部门站），一套站一个结构；
- 数据形态：电商是结构化接口，政策大量正文在 PDF / Word / WPS 附件里，还有扫描件；
- 风控：政策站风控弱，但页面老旧（GBK 编码、表格布局），资源少、响应慢；
- 业务要求：不是"能搜到"，而是"能引用"——发文字号、效力状态必须准，引用了废止文件是事故。

所以技术重心不在对抗风控，而在**规模化适配 + 附件解析 + 要素抽取准确性**。

### 2. 为什么没用 Scrapy？

项目里采集只是第一段，后面还有附件下载、PDF 解析、OCR、要素抽取、去重入库，这些是重活；自研一套轻量调度（asyncio + Redis 队列 + 配置驱动）更好嵌这些步骤，也方便给每个站点做独立的频控和熔断。Scrapy 的中间件、去重能力用 Redis 也能实现，而且团队只有我一个爬虫，没必要为了框架再去维护一层。

> 追问点：**自研调度怎么保证不重复消费？** Redis 用 `BLPOP` 取任务并同时写入 processing 集合，成功后删除；超时未确认的任务由巡检任务重新入队。

### 3. 站点配置化具体怎么做？

一个站点一份 YAML：

```yaml
site: 北京市发改委
encoding: gb2312
list:
  url: https://...
  item: "//ul[@class='list']/li"
  link: "./a/@href"
  pager: {type: page, param: pageNo, max: 20}
detail:
  title: "//h1"
  date: "//span[@class='date']"
  content: "//div[@id='content']"
  attachments: "//div[@class='fj']//a"
```

采集器只认配置，不认站点。改了结构就改选择器；八成以上站点能套进 5 类模板，所以新站点接入从 1 天缩到半天。

> 追问点：**配置写错了怎么快速发现？** 详情页必填字段（标题、正文长度、日期）为空即判定该站点解析失败，进失败队列并告警，不会静默写入空数据。

### 4. 增量采集怎么保证不漏？

三道：

1. 列表页按发布时间做游标，记录每个栏目已采到的最新时间；
2. 每轮带一个时间回扫窗口（比如多扫 2 小时），防止站点审核延迟导致前一轮看不到；
3. 夜间对各栏目做一次翻页到 N 页的兜底扫描，和对已入库条数做比对，数量突变就告警。

实测站点漏采主要不是翻页问题，而是栏目本身改版或被合并，所以站点级健康检查比调度更关键。

### 5. 重复数据怎么处理？

两层：

- URL 层：标准化后（去跟踪参数、统一 http/https）做 Redis 去重；
- 内容层：用「标题 + 发文机关 + 发文字号」生成指纹，同一政策被多个站点转载时只保留主版本（优先发文机关本站），其余标记为转载来源。

项目里重复入库率从 22% 降到 2%。剩下的 2% 主要是多地联合发文，发文字号不同但内容相同，业务上允许保留，已在数据说明里写明。

### 6. 附件解析链路怎么搭的？

下载（限速 + 断点续传）→ 按文件头判断真实类型（不少站点扩展名和内容不一致）→ 分别处理：

- PDF 文本层：pdfplumber 抽文字和页；
- PDF 扫描件：转图片走 OCR；
- Word / WPS：python-docx 读段落与表格，WPS 走格式兼容；
- 附件里再套附件：只下钻一层，避免无限递归。

解析后再洗一遍：去页眉页脚、去"附件："前缀、合并被硬换行切断的句子。附件解析成功率 90%，失败的连同文件地址进人工队列，不丢。

> 追问点：**90% 怎么统计的？** 按周统计下载成功的附件为分母、正文非空且长度超过阈值为分子，失败样本按站点归类，多半是扫描件或加密 PDF。

### 7. OCR 的准确率怎么保证？

先判断是不是扫描件（PDF 无文本层、页面文字数极少）；能拿到文本层绝不用 OCR。OCR 用通用引擎，预处理做灰度、二值化、去噪和 300dpi 放大；识别结果只用于正文检索和摘要，**关键要素（发文字号、日期）不依赖 OCR**，而是用规则在文本层校验、OCR 结果只做兜底，低置信度样本抽检复核。

### 8. 政策要素是怎么抽的？

- 发文字号：正则分机关代字 + 年份 + 序号，如 `京发改〔2024〕15 号`，注意全角半角、六角括号；
- 发文机关：从站点栏目、页面署名和文号代字三处取，建机关词典做归一（"市发改委"→"北京市发展和改革委员会"）；
- 成文日期：优先取文末落款，其次正文日期，统一转 `YYYY-MM-DD`；
- 效力状态：优先取页面上的"废止/失效"标识，没有就默认"有效"，并靠回采更新；
- 主题分类：按业务标签体系做关键词 + 规则匹配，命中多个按优先级取主标签。

抽检 1000 篇，字段准确率 97%；抽不出来的进待校对表，不让空值直接落库。

### 9. 废止和失效怎么跟踪？

两条路：

1. **状态回采**：定期重采已入库政策的原页面，页面出现"已废止/失效"或状态位变化就跟新；
2. **关联检索**：新采到"废止/失效公告"时，从正文里提取被废止的文件名或发文字号，回查政策库做关联标记。

业务价值很直接：咨询报告引用政策前，先看效力状态，避免拿旧文件做依据。

### 10. 政策库怎么支撑检索？

入库时把标题、正文、发文字号、机关、主题标签建成索引字段；检索主要按"机关 + 主题 + 时间 + 关键词"组合，正文用数据库全文索引够用，量大再考虑 Elasticsearch。标题与正文分开存，避免长文本拖慢列表查询。

## 二、稳定性与合规

### 11. 多节点怎么协作？断点怎么恢复？

所有任务进 Redis 队列，多节点用 `BLPOP` 消费（天然不重复）；消费时同时写 processing 集合带时间戳，成功才删；巡检任务定期扫超时未确认的，重新入队。节点挂掉不需要人工补队列，重启继续消费。

### 12. 限速和熔断怎么设计？

按站点维度控速，单站 1 QPS 以内、夜间低峰补量；连续失败（超时、5xx、验证码）达到阈值就熔断该站点，只留少量探测请求；恢复采用半开策略，探测成功率达标再恢复配额。政府站点响应慢，超时阈值设得比商业站宽，避免误判。

### 13. 采集监控看什么？

成功率、失败站点数、附件解析失败数、数据延迟（最新一条入库时间）、单站连续失败次数。告警按站点聚合，避免几千条告警等于没有告警。异常定位时间从半天降到 10 分钟，主要靠"失败站点排行 + 最近错误样本"这两块面板。

### 14. 合规上你怎么把握？

只采公开信息，不碰登录后内容；遵守 robots 与站点声明，控制频率不影响对方服务；联系人、身份证号等字段在入库前过滤；数据仅用于内部咨询研究，不对外分发。上线前和法务/业务一起过一遍站点清单。

## 三、数据质量与业务交付

### 15. 怎么证明数据是"对"的？

- 抽样人工核对：政策抽 1000 篇看要素准确率（97%）；
- 交叉校验：发文字号格式、日期合理性（不能晚于今天）、正文长度阈值；
- 对账：与咨询团队手工整理的样本比对，差异逐条记原因；
- 交付带说明：字段定义、口径、已知问题写进数据说明文档。

### 16. 招投标数据里金额怎么统一？

原始数据元、万元、亿元、费率、下浮率混用。先正则识别单位和数值，统一换算成元；费率类（如"下浮 5%"）不参与金额汇总，单独字段标记；"面议""/""详见公告"这类置空并打标。金额字段准确率 98%，剩余 2% 主要是多标段合计与暂估价，人工复核。

### 17. 企业名称为什么要归一？怎么做的？

同一家公司在不同公告里会写成全角括号、简称、带分公司后缀，甚至"XX 建设集团有限公司"和"XX 建设集团"混用；不归一，业绩统计会把一家拆成好几家。

做法：去空格与全角转半角 → 去通用后缀（有限公司/集团/分公司）→ 简称映射 → 建别名表，冲突时以统一社会信用代码为准（公告里有的情况下）。别名表人工维护，新增企业走审核。

### 18. 招投标公告为什么要按类型分开解析？

招标公告、中标候选人公示、中标结果、变更公告、废标的字段结构完全不同：候选人公示是表格，中标结果是段落，变更公告可能只改一个金额。用一套规则会大量抽空，所以按类型配置解析器，列表页统一处理，进详情前先按标题关键词分类。

### 19. 一次典型的故障排查说一下？

某省级交易中心连续两天入库量掉到平时的三成。先看监控：失败集中在列表页，状态码 200 但条目解析为 0。抓页面发现站点把列表从表格改成了 `div` 结构，选择器失效；因为配置了"解析 0 条即告警"，当天就发现了。改 YAML 选择器后回补两天数据，入库量恢复。之后把"关键站点改版"纳入每周巡检，抽 3 个站点比对条目数。

## 四、常见反问

- **为什么做爬虫？** 喜欢和数据、和站点结构打交道；在咨询公司做采集，能直接看到数据被用在报告和决策里，反馈比较实在。
- **你觉得这份工作最难的地方？** 不是写请求，是"数据对不对、能不能被引用"——政策要素和效力状态错了，业务方会直接引用错文件。
- **最近在学什么？** 说一个能落地的方向，比如政策文本的分类与摘要、Elasticsearch 检索、或 Playwright 与接口混合采集，别报菜名。
- **能不能接受写文档/对接业务？** 可以，采集的口径本来就是和业务一起定出来的，交付文档也是我一直在维护的。
